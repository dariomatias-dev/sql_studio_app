# Contributing

## Setup

After cloning, enable the repo's git hooks:

```bash
git config core.hooksPath .githooks
```

This activates a `commit-msg` hook that rejects commits not following the
convention below.

## Commit convention

This project follows [Conventional Commits](https://www.conventionalcommits.org):

```
<type>(<scope>): <subject>
```

- **type**: `feat`, `fix`, `refactor`, `docs`, `style`, `test`, `chore`, `perf`, `build`, `ci`, `revert`
- **scope**: optional, lowercase, e.g. `database`, `sql_editor`, `settings`
- **subject**: imperative mood, no trailing period, ≤72 chars

Examples:

```
feat(database): add favorite toggle to database card
fix(database_visualizer): stop caching usecase in late field
refactor(ui): centralize color and shadow tokens
```

Body (optional) explains *why*, not *what* — the diff already shows what
changed.

## Branching

- `main` is protected: no direct pushes, merges only via pull request.
- Branch names: `<type>/<short-description>` (e.g. `feat/database-favorites`,
  `fix/visualizer-crash`).

## Pull requests

- One logical change per PR; keep it small and reviewable.
- CI (`analyze-and-test`) must pass before merge.
- Squash or rebase merge only — no merge commits, to keep history linear
  and each entry a valid Conventional Commit.
- For this repo (single maintainer), self-merge after CI passes is allowed;
  branch protection still requires the PR flow and passing checks.

## Code style

- Follows `very_good_analysis` lints — run `flutter analyze` before pushing.
- Run `dart format lib/src lib/main.dart test` before committing (`lib/l10n`
  is generated by `flutter gen-l10n` and excluded from formatting/lint,
  same as in `analysis_options.yaml`).

## Tests

- `flutter test` runs the unit test suite in `test/`.
- Prefer testing use cases with real branching logic and view models over
  use cases that only forward to a single repository method — those add
  no coverage beyond the mock itself.
